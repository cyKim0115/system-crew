# Workflow: Idea Evaluation

사용자가 **시스템·구현 방법 아이디어**를 제시하며 “판단해서 적용해줘”라고 할 때 따른다.  
무조건 수용하지 않는다. **실현 가능성 / 방향성 / 효율**을 객관적으로 평가한 뒤 `ADOPT` | `ADOPT_WITH_CHANGES` | `DEFER` | `REJECT`를 내린다.

## 트리거

- “이렇게 하면 어떨까 / 이 방식으로 해줘 / 적용해볼래” + 구체적 방법·구조 제안
- 참고 재현 중 사용자가 대안 구현을 제안할 때
- 기존 스펙을 바꾸는 설계 제안

단순 버그 수정·명백한 스펙 이행은 이 워크플로를 건너뛴다.

## 역할

| 단계 | 담당 |
|------|------|
| 아이디어 접수·범위 고정 | Producer |
| 시스템/플레이 적합성 | Systems Analyst |
| 기술·유지보수·성능 실현성 | Implementer (자문) |
| 종합 판정·다음 행동 | Producer (또는 명시적 Idea review 요청 시 Analyst 주도) |

한 응답 안에서 협의하되, **판정 전에는 본구현하지 않는다**.

## 평가 축 (필수)

1. **Feasibility (가능한가)**
   - 현재 엔진·패키지·코드베이스로 구현 가능한가
   - 리스크·미지수·필수 선행 작업은 무엇인가
2. **Direction fit (어울리는가)**
   - 프로젝트 기존 패턴·아키텍처와 맞는가
   - 참고 목표(`faithful`/`inspired`)·제품 방향과 충돌하지 않는가
   - 범위가 한 시스템/수직 슬라이스를 넘지 않는가
3. **Efficiency (효율적인가)**
   - 이득 대비 구현·유지 비용이 합리적인가
   - 더 단순한 대안이 있는가
   - 성능·복잡도·중복을 불필요하게 키우지 않는가

각 축에 `Pass` / `Partial` / `Fail`와 근거 1–3문장을 남긴다.

## 판정

| Verdict | 의미 | 다음 행동 |
|---------|------|-----------|
| `ADOPT` | 제안 그대로 적용 | 스펙/구현으로 진행 |
| `ADOPT_WITH_CHANGES` | 방향은 수용, 방법 수정 | 수정안 제시 → 사용자 확인 후 진행 |
| `DEFER` | 가치 있으나 지금 아님 | 이유·재검토 조건 기록, 현재 범위에서 제외 |
| `REJECT` | 비효율·부적합·비현실 | 근거 + 대안 1개 이상 제시 (가능하면) |

`Partial`/`Fail`가 있어도 다른 축이 강하면 `ADOPT_WITH_CHANGES`가 될 수 있다.  
**세 축 모두 Fail에 가까우면 `REJECT`**.

## REJECT vs 실험 재시도

- `REJECT`는 **제품 채택**을 거절한 것이다. 같은 접근을 영구 금지하라는 뜻이 아니다.
- 사용자가 **시간 제한 실험**(비교용 브랜치·프로토타입)을 명시하면 새 idea log로 재판정할 수 있다. 보통 `ADOPT_WITH_CHANGES` + 「실험 전용 / 제품 머지 보류」.
- 실험 결과가 나와도 제품 채택은 **별도 판정**이다. 이전 `REJECT` 기록을 덮어쓰지 말고 새 항목(또는 Follow-up)으로 남긴다.

## 경쟁 안 비교 (시각·체감이 핵심일 때)

서로 배타적인 구현 안을 before/after로 비교해야 하면:

1. 한 브랜치에 토글만 몰아넣지 말고, 기준 브랜치에서 `exp/<slug>-a`, `exp/<slug>-b` …처럼 **안별 브랜치**를 쓴다.
2. Idea log에 브랜치 목록·성공 기준·「지금은 제품 브랜치에 머지하지 않음」을 적는다.
3. 각 안 완료 시 before/after 캡처(스크린샷 등)로 비교 가능하게 한다.
4. 제품 머지는 비교·피드백 후 **별도 `ADOPT*`**.

## 산출물

1. `templates/idea-evaluation.md` 형식으로 작성
2. 저장 위치 (소비 프로젝트):
   ```text
   docs/decisions/ideas/
     INDEX.md
     YYYYMMDD-short-slug.md
   ```
3. `ADOPT*`면 관련 `system-spec` / reference asset Decisions 표에 반영
4. `REJECT`/`DEFER`여도 INDEX에 남겨 같은 제안을 반복 논의하지 않게 한다
5. **rag가 탐지되면** (형제 `../rag` / `RAG_ROOT` / `capture-to-rag` 스킬 기본 경로): 판정 요약을 `capture-to-rag`로 남길지 **검토**한다. 기본은 제안만; 사용자가 원하면 즉시 캡처. 소비 프로젝트 `docs/decisions/` 기록을 대체하지 않는다.

## 톤

- 사용자를 무시하지 않는다. **거절도 근거·대안으로** 말한다.
- “취향”만으로 거절하지 않는다. 취향 이슈면 Direction fit에 **프로젝트 기준**으로만 적는다.
- 확신이 낮으면 Hypothesis로 표시하고, 막히는 검증만 짧게 질문한다.

## Cursor 호출 예

- `이 아이디어 평가해줘. Coroutine 대신 상태머신으로…`
- `적용할지 판단하고, 괜찮으면 반영해`
- `거절해도 되니까 객관적으로 봐줘`
